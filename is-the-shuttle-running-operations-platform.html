Technical build story · Java / Spring Boot

Building a shuttle status and driving history app.

Is the Shuttle Running? answers a small, practical question for riders while keeping an accurate record of the driving behind it. I built the application through Renatus, drawing on my experience in employee transportation and wardrobe operations.

The current product

A clear status and a record of actual service.

Riders check status

A public page shows whether the shuttle is running and the active driver’s first name. It has no schedules, pickup instructions, or ride-confirmation button.

Drivers record the run

Signed-in drivers use an NFC or QR checkpoint to start, pause, resume, end, or hand off service. Each actual driving segment becomes part of the history.

Managers review history

Date and driver filters show who drove, when they started and stopped, and how much time they drove. Paused time is excluded, and managers can close forgotten runs.

Product judgment

Why I removed shift assignment.

The earlier version imported employee schedules and planned driving coverage. But an assignment did not establish that a shuttle was actually operating. I narrowed the product to recorded service, public status, and history.

That change affected more than the navigation. New runs no longer need an assignment. Existing assignment-linked records still appear in the history, applied database migrations stay intact, and retired planning submissions are rejected before their old handlers run. The repository labels retained planning code and the older illustrated walkthrough as historical material.

Implementation

The decisions behind the screens.

One server-rendered Java 17 / Spring Boot application, with Spring MVC, Spring Security, Thymeleaf, Spring Data JPA, MySQL, and Flyway.

Transactional session changes

Checkpoint actions lock the organization and read the active session for update. A handoff closes the old segment and opens the next in one transaction; stale action forms are rejected.

Organization-aware access

Authentication alone is insufficient. Services check membership and resource ownership, and drivers must use their own account. Possessing a tag link does not replace those checks.

Time within the selected range

Reports use the operations timezone and clip overlapping runs to the requested dates. Active runs contribute elapsed time. Pauses create no driving segment and add no driving time.

A minimal public model

The rider controller supplies an organization name, a binary running state, and the active driver’s first name. Operational notes and internal records stay outside that view.

Explicit session endings

Phone inactivity is not proof that the shuttle stopped. Drivers or managers end sessions explicitly. The tradeoff is that forgotten runs can leave stale status until corrected.

Tests against the actual database

JUnit and Spring integration tests use MySQL through Testcontainers. GitHub Actions runs the Java and JavaScript checks and builds the production Docker image.

My role and the boundaries

From requirements to ongoing changes.

I worked on the requirements, Java services, relational schema, role-specific screens, NFC/QR workflow, tests, deployment configuration, and maintenance. Development includes AI assistance; the source and tests provide concrete material for technical review.

The application models one active service per organization, rather than a multi-vehicle fleet. Public status reflects recorded driver actions and temporary manager overrides; it is not an arrival prediction. Those boundaries keep the current workflow small and make the remaining tradeoffs explicit.
